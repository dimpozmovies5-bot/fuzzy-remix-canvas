1. OVERVIEW OF THE WHOLE SYSTEM
================================================================================
- Users sign in with Firebase Auth (email/password or Google).
- On every auth state change the app writes/refreshes users/{uid}.
- A user MUST save a phone number before using the app (blocking dialog).
- Content (movies, series, music, animation, carousel) is public read,
  admin-only write. So the app can show posters even before login.
- Watching/downloading requires an ACTIVE SUBSCRIPTION stored at
  subscriptions/{uid}. Admin bypasses this.
- Subscriptions are bought with Mobile Money: the app calls the Railway
  backend (/api/deposit), then polls /api/request-status until success,
  then writes subscriptions/{uid} itself.
- Plans are NOT hardcoded — they live at subscription_plans and the admin
  edits them from the dashboard. One or more plans can be flagged isAgent.
- Agent plan holders get the Agent Zone: content flagged isAgent = true,
  which is uploaded there first and later moved to normal listings by admin.
- Trending badges come from a per-content view counter at content_views/{id}.

3. SECURITY RULES — WHO CAN DO WHAT
================================================================================
The live rules file is database.rules.json in this project. Summary:

PUBLIC READ (no login): movies, series, originals, music, animation,
carousel, content_updates, content_views.
ADMIN-ONLY WRITE on all of those (auth.token.email == arthurdimpoz@gmail.com).

OWNER-OR-ADMIN read+write: users/{uid}, subscriptions/{uid},
continueWatching/{uid}, watchHistory/{uid}, agent_profiles/{uid},
user_notifications/{uid}, push_subscriptions/{uid}, fcm_tokens/{uid}.

ANY SIGNED-IN USER may write (append) to: transactions, navigation_activity,
user_activity, analytics, content_views/{id}, wallet.
Only admin may READ those.

notifications: read by anyone signed in, written by admin, but each user may
write notifications/{id}/readBy/{ownUid}.

IMPORTANT: rules must be published in the Firebase console
(Realtime Database > Rules > paste database.rules.json > Publish),
otherwise saving agent profiles, plans or views is rejected with
"PERMISSION_DENIED".

If you add subscription_plans editing from the app, the rules need:
  "subscription_plans": {
    ".read": true,
    ".write": "auth != null && auth.token.email === 'arthurdimpoz@gmail.com'"
  }
and for agent flags on content nothing extra is needed (isAgent is just a field,
but add ".validate": "newData.isBoolean()" for isAgent / isCompleted if you
keep strict per-field validation).

ON EVERY AUTH STATE CHANGE the app does exactly this (mirror it in mobile):
  onAuthStateChanged(auth, async (currentUser) => {
    if (!currentUser) { /* clear state */ return; }
    const userRef = ref(database, `users/${currentUser.uid}`);
    const snap = await get(userRef);
    await set(userRef, {
      email: currentUser.email,
      displayName: currentUser.displayName || currentUser.email.split("@")[0],
      photoURL: currentUser.photoURL,
      phoneNumber: currentUser.phoneNumber || snap.val()?.phoneNumber || "",
      lastLogin: new Date().toISOString(),
      createdAt: snap.exists() ? snap.val().createdAt : new Date().toISOString(),
      isAdmin: currentUser.email.toLowerCase() === "arthurdimpoz@gmail.com",
    });
  });
Note: set() REPLACES the node. Keep createdAt and phoneNumber as shown, or use
update() instead if you add more fields in the mobile app.

ADMIN DETECTION: lowercase+trim the email and compare with
"arthurdimpoz@gmail.com". Admin also passes the extra dashboard code stored at
adminSettings/password (read it, compare, then allow the dashboard).

Web-only extra: on login the app clears stale payment keys from
localStorage/sessionStorage and payment URLs from the cache, once per 30 min,
so a failed payment does not block a retry. On mobile the equivalent is: do not
cache /api/deposit or /api/request-status responses, and clear any stored
pending reference when a payment ends.

5. PHONE NUMBER — COMPULSORY, THEN EDITABLE
================================================================================
Right after login, read users/{uid}/phoneNumber. If it is missing or invalid,
show a BLOCKING dialog that cannot be dismissed until a valid number is saved.

Normaliser (use this exact logic everywhere):
  strip everything except digits and a leading +
  if it starts with "+", drop the +
  if 10 digits starting with "0"  -> "256" + rest         (0773566069)
  else if 9 digits starting with "7" -> "256" + all       (773566069)
  reject if fewer than 8 or more than 15 digits
  result = "+" + digits          e.g. "+256773566069"
This accepts local Ugandan numbers AND any international number.

Save with UPDATE (never set, or you wipe the user node):
  await update(ref(database, `users/${uid}`), {
    phoneNumber: normalized,
    email: user.email,
    phoneUpdatedAt: new Date().toISOString(),
  });

Editing later: the Settings screen reads users/{uid}/phoneNumber, lets the user
change it, and writes it back with the same update() + normaliser.

6. SUBSCRIPTION PLANS — LIVE FROM THE DATABASE
================================================================================
Listen (do not one-shot read) so admin edits appear instantly:
  onValue(ref(database, "subscription_plans"), snap => {
    const val = snap.val();
    const plans = !val ? DEFAULT_PLANS :
      Object.entries(val).map(([id, p]) => ({
        id,
        name: p.name ?? id,
        duration: p.duration ?? "",
        price: Number(p.price) || 0,
        days: Number(p.days) || 0,
        isAgent: p.isAgent === true,
        order: typeof p.order === "number" ? p.order : 99,
      })).sort((a,b) => (a.order-b.order) || (a.price-b.price));
  });
If the node is empty the app falls back to the default list in section 2.

ADMIN writes a plan:
  await set(ref(database, `subscription_plans/${planId}`), {
    name, duration, price: Number(price), days: Number(days),
    isAgent: !!isAgent, order: Number(order),
  });
ADMIN deletes a plan:
  await remove(ref(database, `subscription_plans/${planId}`));
Deleting a plan does not cancel existing subscriptions; they keep working until
endDate because subscriptions/{uid} stores planName, days-derived endDate etc.

7. PAYMENT FLOW (MOBILE MONEY) — STEP BY STEP
================================================================================
Backend base URL:
  https://function-bun-production-f6bb.up.railway.app/api

Endpoints:
  POST /api/deposit          { msisdn, amount, description }  -> start collection
  POST /api/withdraw         { msisdn, amount, description }  -> send money
  POST /api/validate-phone   { msisdn }                       -> check operator
  GET  /api/wallet/balance                                    -> float balance
  GET  /api/request-status?internal_reference=XXXX            -> poll a request
  GET  /api/transactions                                      -> backend list

FULL PURCHASE SEQUENCE:
 1. User picks a plan (from subscription_plans).
 2. App asks for the phone number (prefill users/{uid}/phoneNumber),
    normalise it with the section-5 normaliser (must be +2567...).
 3. Optional: POST /api/validate-phone to confirm the number is MTN/Airtel.
 4. POST /api/deposit with
      { msisdn, amount: plan.price, description: "LUO CINEMA <plan.name> Subscription" }
    Response contains success + internal_reference
    (sometimes nested: result.internal_reference OR result.relworx.internal_reference).
 5. Immediately record the attempt:
      set(ref(database, `transactions/${internal_reference}`), {
        userId, userEmail, planId, planName, amount, msisdn,
        referenceId: internal_reference, status: "pending",
        timestamp: new Date().toISOString(),
      });
 6. Show "Payment prompt sent — approve on your phone".
 7. POLL GET /api/request-status?internal_reference=... every 1 second,
    max ~90 attempts (90 s), then time out.
    Status can appear as res.request_status, res.status,
    res.relworx.request_status or res.relworx.status.
      "success"   -> set transactions/{ref}/status = "successful",
                     ACTIVATE the subscription (section 8), show success
      "failed" / "cancelled" -> set status accordingly, show the message
      anything else -> keep waiting
 8. ALWAYS stop the poll timer when leaving the screen.
 IMPORTANT: url-encode internal_reference in the query string.

If /api/deposit returns an error mentioning INVALID_IP, that is a Relworx
whitelist problem on the payment server, not the app: the Railway service's
outbound IP must be whitelisted in the Relworx dashboard (enable a static
outbound IP in Railway > Networking, then whitelist that IP).

8. ACTIVATING, CHECKING AND EXPIRING A SUBSCRIPTION
================================================================================
ACTIVATE (after a successful payment):
  const now = new Date();
  const end = new Date(now.getTime() + plan.days * 24*60*60*1000);
  await set(ref(database, `subscriptions/${uid}`), {
    planId: plan.id, planName: plan.name,
    startDate: now.toISOString(), endDate: end.toISOString(),
    active: true, amount: plan.price, paymentRef: internal_reference,
  });

CHECK on app start and after login:
  const snap = await get(ref(database, `subscriptions/${uid}`));
  if (!snap.exists()) -> no subscription
  else {
    const data = snap.val();
    if (new Date(data.endDate) > new Date())  -> ACTIVE
    else { await set(ref, {...data, active: false}); -> EXPIRED }
  }
hasActiveSubscription = exists && active === true && endDate > now.
Never trust active alone — always re-compare endDate, because nothing runs
server-side to flip it.

Admin can hand-set any dates, e.g. to start a 1-week plan at 08:30:
  set(ref(database, `subscriptions/${uid}`), {
    planId: "1week", planName: "1 Week Pass",
    startDate: "2026-07-14T08:30:00.000Z",
    endDate:   "2026-07-21T08:30:00.000Z",
    active: true, amount: 12000,
  });

isAgentSubscriber = hasActiveSubscription AND the plan whose id ==
subscriptions/{uid}.planId has isAgent === true.

12. FETCHING SERIES, SEASONS AND EPISODES
================================================================================
Read series exactly like movies, from the "series" node.

THE EPISODE TRAP: Firebase returns episodes either as an ARRAY (possibly with
null holes) or as an OBJECT keyed "0","1",... Always normalise:

  function normaliseEpisodes(raw) {
    if (!raw) return [];
    const arr = Array.isArray(raw) ? raw.filter(Boolean) : Object.values(raw);
    return arr.map((ep, i) => ({
      episodeNumber: ep.episodeNumber != null ? Number(ep.episodeNumber) : i + 1,
      title: ep.title || `Episode ${i + 1}`,
      streamlink: ep.streamlink || ep.videoUrl || "",
      season: Number(ep.season || 1),
    })).sort((a,b) => a.season - b.season || a.episodeNumber - b.episodeNumber);
  }

Seasons list:  [...new Set(episodes.map(e => e.season))].sort()
Episodes of a season:  episodes.filter(e => e.season === activeSeason)
Total episode count (poster badge):  episodes.length
Seasons count: item.seasons ?? number of distinct seasons

Playing an episode: use that episode's streamlink. Deep link pattern used by
the website: /play/{id}?type=series&ep={episodeNumber} — keep the same
parameters in the mobile route so links work in both.

16. PLAY SCREEN — GATING, STREAMING, DOWNLOADS
================================================================================
Order of checks when the screen opens:
  1. no user            -> go to Login
  2. not admin AND not hasActiveSubscription -> go to Subscribe
  3. item.isAgent === true AND not agent subscriber AND not admin
                        -> show the Agent plan upsell instead of the player
  4. otherwise load the content from its node and play.

Stream URL: movies -> streamlink (fallback videoUrl); series -> the selected
episode's streamlink. Use ExoPlayer (Android) / AVPlayer (iOS) /
video_player or better_player (Flutter). Nothing about the URL is secret to the
player — the gate is the subscription check in the app.

DOWNLOAD: same URL saved to device storage. Download limits (client-side,
stored locally under key "download_tracker_v2"):
  - plan "12hr": 10 downloads total for the period; already-downloaded items
    can be re-downloaded free of charge
  - every other plan: unlimited
Track { planId, subscriptionStart, downloads: [contentIds], daily: {} } and
reset it whenever planId changes.

Also on this screen: rating, year, category/genre, description, share link, and

25. COMMON ERRORS AND HOW TO AVOID THEM
================================================================================
PERMISSION_DENIED writing agent profiles / views / plans
   -> the rules in database.rules.json were never published. Publish them.
Poster shows but nothing plays
   -> streamlink empty, or the item is a series and you used the top-level
      streamlink instead of the episode's.
Episodes missing or shifted
   -> you did not normalise the array/object shape (section 12).
Subscription still "active" after it ended
   -> always compare endDate with now; nothing flips active server-side.
Payment always fails with INVALID_IP
   -> Relworx whitelist on the payment server, not the app.
"Payment Failed / Try again" straight away
   -> msisdn was not normalised (e.g. "+256256770...") or the amount was sent
      as a string. Normalise once, send a Number.
Country code doubled
   -> only prepend 256 when the number is a 10-digit 0-prefixed or 9-digit
      7-prefixed local number.
User node loses fields after login
   -> set() replaces; carry createdAt/phoneNumber over or use update().
rating/year rejected
   -> they must be numbers, within the validated ranges.
Agent content visible to everyone
   -> the normal listings forgot `.filter(i => i.isAgent !== true)`.
